# TG-MAX Ultimate — анализ MAX и план перехода на интерфейс Telegram

Актуализация 14 ноября 2026 года: основа заменена на официальный DrKLO/Telegram 13.2.2; из NagramXF переносятся только выбранные локальные функции. Разрешён QR-вход через MAX. В меню входа семь языков, португальский без региона выбирает бразильский вариант. Подробности реализации и текущие ограничения — в [актуальной архитектуре](telegram-migration.md). Оставшаяся часть документа сохраняет первоначальный план и разбор исходных скриншотов от 8 ноября.

Дата проверки: 8 ноября 2026 года. Платформа: Android. Визуальная база: исходники NagramXF, указанные заказчиком. Документ описывает целевое устройство приложения и порядок разработки; наличие строки в плане не означает готовую функцию.

## 1. Зафиксированная цель

TG-MAX — клиент личного аккаунта MAX: профиль, переписка, группы, каналы, истории, медиа и звонки работают через MAX. Интерфейс, навигация, ячейки, пузыри, редакторы, жесты и анимации берутся из выбранной версии NagramXF/Telegram. Пользователь видит только данные MAX. Telegram MTProto, Telegram-сессии и Telegram backend должны быть удалены из активного приложения.

«1:1» определяется относительно конкретного коммита NagramXF, а не сразу всех версий Telegram Android, iOS и Desktop. Сохраняем существующие компоненты и их размеры/темы, а не рисуем приблизительную копию в новом Compose/Web UI. Для функций MAX без аналога Telegram создаём новые экраны из тех же Telegram-компонентов. Для них невозможно честно обещать совпадение с несуществующим исходным экраном Telegram.

Вход — по номеру телефона; QR-авторизация исключена по ранее согласованному требованию. QR собственного профиля для обмена контактом — отдельная функция. Языки: ru, en, es, uz (латиница), pt, pt-BR, fr, be; других языков не добавляем.

## 2. Что действительно находится в архиве

Архив Screenshots.zip содержит **45 JPG, каждый 1080 × 2400**, снятых 8 ноября 2026 года между 20:16:53 и 20:23:08. SHA-256 архива: `c4f119b7e5dc3bb14bd3ae24f4a83a969c018f032cb5cb809ac964a46222716f`. Ниже каждому файлу назначен постоянный ID S01–S45 в хронологическом порядке. Повторные кадры с прокруткой, меню и клавиатурой учтены отдельно как состояния одного экрана.

Наблюдения, влияющие на архитектуру:

- S03 требует **позвонить с собственного номера на номер сервиса**, а не только получить SMS. Номер получателя и срок действия должны приходить из реального challenge.
- S04 показывает пароль, S05 — код из почты и восстановление доступа. Нельзя ограничивать вход цепочкой «телефон → SMS → готово».
- S13 включает семейную защиту, безопасный режим и несколько разных правил приватности. Их значения не совпадают автоматически с правилами Telegram.
- S14 действительно показывает QR-вход MAX. Это расходится со старым предположением об отсутствии QR в MAX, но не меняет согласованный для TG-MAX сценарий входа по телефону.
- S07 содержит папки, счётчики и ряд историй. S27–S31 — собственные истории, выбор медиа и редактор. Значок текста в редакторе не является доказательством AI-функции.
- S08 показывает вход в Сферум и вкладку «Цифровой ID»; их внутренние экраны в архиве отсутствуют.
- S40 показывает версию исходного MAX 26.39.0. Исследуемый WhiteMAX основан на другой версии, а MAX-decompiled ещё старше; их контракты нельзя объявлять актуальными только по сходству названий.

В архиве нет полноценного непустого экрана переписки: S26 — пустое «Избранное», S32–S33 — preview темы. Также нет открытого звонка, просмотра чужой истории, управления каналом/группой, внутренних страниц семейной защиты, Сферума и Цифрового ID. Их дизайн берём из Nagram, а поведение отдельно исследуем по MAX; не выдаём это за наблюдение на скриншотах.

Персональные имена, номера, адрес почты, IP и содержимое переписки из снимков в спецификацию не переносятся. В тестах используются синтетические данные.

## 5. Навигация и визуальный стандарт

Старт после входа — DialogsActivity. Ряд историй, папки и список чатов сохраняют расположение и поведение выбранного Nagram. Создание личного чата/группы/канала — через стандартную точку входа Telegram. Контакты, звонки, «Избранное» и настройки доступны через существующую навигацию Nagram; не переносим четыре нижние вкладки MAX поверх неё. Цифровой ID и Сферум получают строки в разделе «Сервисы MAX», поскольку отдельной стандартной вкладки Telegram для них нет.

Профиль собеседника открывается из заголовка ChatActivity. Медиа — SharedMediaLayout. Канал использует Telegram-экран переписки с соответствующими правами и доступными действиями; каталог S43 — отдельный экран поиска/обзора. «Рекомендованный» и «подписанный» канал — разные состояния. Экран управления каналом не показан в архиве и проектируется отдельным сценарием.

Для визуального совпадения повторно используем ActionBar/BaseFragment, RecyclerListView, DialogCell, ChatMessageCell, TextSettingsCell, TextCheckCell, EditTextBoldCursor, BottomSheet/AlertDialog, Theme и оригинальные drawables. Конкретные размеры/радиусы/отступы читаются из выбранного исходника. Не задаём их по пикселям MAX-скриншотов. Светлая/тёмная темы, длинные переводы, крупный шрифт, IME, insets и TalkBack входят в приёмку.

Эталон сравнения: одинаковый коммит Nagram, устройство/разрешение, density, fontScale, тема и локаль, плюс синтетические fixtures. Для UI делаем overlay/diff эталонного Nagram и TG-MAX: ActionBar, папки, ряд историй, строки диалогов, входящие/исходящие пузыри, выбранные сообщения, клавиатура, popup, настройки. Маскируем только изменяемые данные/время/брендинг. Новые MAX-only экраны оцениваем по тем же компонентам и правилам, а не объявляем существующими экранами Telegram.

## 6. Архитектура

### 6.1. Граница системы

Слои целевого клиента:

1. **Nagram UI.** Существующие Android UI-компоненты и навигация; без прямых URL/опкодов MAX в экранах.
2. **Nagram compatibility / presentation.** Преобразует MAX-доменные сущности в объекты представления, которые понимают существующие UI-контроллеры. На старте может возвращать TLRPC-объекты локально. TLRPC здесь — формат совместимости в памяти, не сетевой протокол.
3. **MAX domain services.** Auth, Dialogs, Messages, Contacts/Profile, Folders, Media/Stickers, Stories, Calls, Privacy/Sessions, Notifications. Источник прав, допустимых действий и состояния — MAX.
4. **MAX transport и sync.** Соединение, handshake, запрос/ответ, push, таймауты, восстановление, курсоры, дедупликация. Отдельно MAX upload/download и отдельный call signaling/media path.
5. **Local state.** Успешная сессия в Android Keystore-backed store, устойчивые таблицы идентификаторов, MAX-кэш и outbox. Старые Telegram caches не смешиваются с MAX-аккаунтом.

Базовая цепочка: `Nagram UI → presentation adapter → MAX services → MAX transport → MAX servers`. Ответы и события возвращаются через MAX state/cache и обновляют представление. UI не должен самостоятельно отправлять MAX-пакеты или интерпретировать transport error strings.

### 6.2. Где менять Nagram

| Узел Nagram | Изменение |
|---|---|
| `ConnectionsManager` / JNI `tgnet` | На переходном этапе единая точка маршрутизации запросов в MAX. Завершённый продукт не инициализирует MTProto и не имеет запасного Telegram backend. Сам запрет нескольких Java-вызовов не заменяет полный аудит. |
| `MessagesController` / `MessagesStorage` | Привязать диалоги и projection-кэш к MAX; убрать Telegram-specific difference/access-hash предположения. События и порядок — из MAX sync. |
| `SendMessagesHelper` | MAX outbox, cid/random-id корреляция, edit/delete/reply и uploads. Нельзя автоматически повторять отправку после неоднозначного timeout без проверки результата. |
| `FileLoader` / `ImageLoader` | Загрузка MAX файлов и обновление истёкших URL; не вызывать Telegram file locations/DC/file references. Оставить декодирование/кэш/UI там, где оно независимо от сети. |
| `LoginActivity` | Заменить бизнес-логику авторизации на MAX AuthFlow. Для исходящего звонка/пароля/email используются те же UI-компоненты, но собственные состояния. |
| `StoriesController` + `ui/Stories` | MAX stories service/IDs/expiry/privacy/uploads; сохранить rings/viewer/recorder UI. |
| `VoIPService` + `VoIPFragment` / `CallLogActivity` | UI и аудиоустройства повторно использовать; Telegram call RPC, ключи и signaling заменить отдельной реализацией MAX. |
| Privacy/Sessions/Settings/Filters | Перепривязать каждую строку к MAX или локальному состоянию; неизвестные серверные переключатели не показывают ложный успех. |

Сначала проверяем и исключаем все оставшиеся Telegram-сетевые пути: отправка RPC, файлы, авторизация, stories, звонки, push registration, языковые пакеты, updater, рекомендации и deep links. Для разработки остаётся fail-closed ошибка неизвестной операции; в пользовательском релизе связанные неподдержанные действия должны быть скрыты или явно недоступны. Основные функции не должны зависеть от Telegram-домена, даже когда он доступен.

### 6.3. MAX-модели и Telegram UI

| MAX-сущность | Собственная модель | Представление в Nagram / ограничения |
|---|---|---|
| contact/profile | `MaxUser`, `MaxProfile`, `Presence` | Telegram User/Profile; имя/аватар/online/bot/verified из MAX. Не придумывать Telegram username/access_hash. |
| `DIALOG` | `MaxDialog(kind=PRIVATE)` | Диалог с peerUser; MAX chatId хранится отдельно от userId. |
| `CHAT` | `MaxDialog(kind=GROUP)` | Групповой ChatActivity; участники/права/название из MAX. |
| `CHANNEL` | `MaxDialog(kind=CHANNEL)` | Channel UI; возможность публиковать определяется MAX role/rights, не видом пузыря. |
| message | `MaxMessage` с serverId, chatId, cid, time, sender, version, body, reply, attaches | ChatMessageCell/MessageObject; delivery/read/edit/delete раздельно, timestamps в согласованных единицах. |
| attachments | Типизированные photo/video/audio/file/sticker/contact/link payloads | Telegram media cells после явного mapping. Форматирование и offsets проверять на emoji/UTF-16. Неизвестное вложение — видимое состояние, а не пустой пузырь. |
| folder | `MaxFolder` с include/filter/options/order | Telegram tabs и editor; сохранять реальные MAX predicates, включая непрочитанное/со звуком. |
| story | `MaxStory`, `StoryOwner`, expiresAt, media, privacy, views | Telegram rings/viewer/recorder; история пользователя и история канала — разные owners. Истёкшее не остаётся активным кольцом. |
| call | `MaxCall`, `CallSession`, `CallLogEntry` | Telegram журнал/экран звонка; MAX conversationId, signaling, media и события жизненного цикла. |
| privacy/session | `MaxPrivacyRule`, `MaxSession` | Telegram settings cells/SessionsActivity; реальный серверный scope, исключения и отзыв. |

**Идентификаторы.** Не приводить MAX IDs к `int` и не проводить их через JavaScript Double. Хранить исходные ID без потерь и per-account mapping к локальным UI IDs. Если Telegram ожидает int32 message/story ID, использовать отдельную устойчивую таблицу и обратный индекс; сортировка/пагинация остаётся по серверному курсору/времени, а не случайному локальному номеру. Удаление, reply и read mark всегда переводятся обратно в исходный MAX ID.

**Синхронизация.** Применение push, запись в кэш и изменение MAX cursor выполняются атомарно. Event identity/version нужны для дедупликации, поздних edits и deletes. После reconnect идёт подтверждённая серверная досинхронизация; возвращать искусственный Telegram `differenceEmpty` вместо неё в готовом клиенте нельзя. Нужны тесты потери сети между server-ack и local-commit. Кэш Nagram допустим как projection для UI, но не второй независимый источник истины.

**Outbox.** Локальный optimistic message имеет статус pending, cid и привязку к последующему MAX serverId. Timeout отправки — неоднозначный исход: сначала reconciliation по cid/истории, затем решение о повторе. Read/delivered подтверждаются конкретным MAX событием; наличие объекта в кэше не означает прочтение.

### 6.4. Авторизация: обязательное расширение

Целевой AuthFlow имеет состояния `PhoneEntry`, `RequestingChallenge`, `WaitingCode`, `WaitingOutgoingCall`, `WaitingPassword`, `WaitingEmailCode`, `RegisterProfile`, `Authorized`, а также expired/rate-limited/recoverable error. Сервер определяет доступные следующие шаги. Не задаём единственную фиксированную последовательность для всех аккаунтов.

`AuthChallenge` содержит безопасный публичный вид (тип шага, маска получателя/номер сервиса, codeLength, expiresAt/resendAt), а token/trackId остаются только в памяти auth service. Для звонка открывается системный dialer через действие пользователя; завершение вызова само по себе не означает успешную серверную проверку. Для email различаются обычная проверка, восстановление и отсутствие доступа к почте. Password MAX не передаётся в Telegram SRP.

Komet содержит реальную проверку `passwordChallenge`/`trackId` и `authLoginCheckPassword`, а также управление 2FA. Но по просмотренному RequestCodeResult он извлекает прежде всего token. Скриншоты S03/S05 требуют дополнительного исследования полных challenge/restore-контрактов; их нельзя объявить готовыми по одному списку opcode. Ни номер сервиса, ни email, ни интервалы не копируются со снимка.

При успехе сохраняется только действительная MAX-сессия; OTP, пароль и временный challenge не попадают в saved state, обычные prefs, логи или отчёт. При logout локальная сессия очищается даже при сетевом сбое; отзыв на сервере проверяется отдельно.

### 6.5. Медиа, истории и звонки — отдельные подсистемы

Медиа: получение upload URL/credentials → загрузка → подтверждение attachment → отправка сообщения. Скачивание требует заголовков, ограничений доступа, возобновления и обновления истёкшего URL. Прямо переиспользовать Telegram FileLoader с Telegram document/access_hash недостаточно.

Истории: MAX list/get/mark/publish, owner namespaces, срок жизни и собственный архив. Komet действительно содержит получение/отметки и публикацию photo/video media; поддержка всех инструментов S31 из этого не следует. Telegram редактор может локально рендерить текст/кисть в допустимый файл. Кликабельные ссылки/mentions требуют поддерживаемых MAX entities; рисовать ссылку на картинке как будто она интерактивная нельзя.

Звонки: отдельный MAX signaling и WebRTC/media transport. В Komet обнаружены MAX conversation endpoint и отдельный ws2 signaling; это не Telegram phone.requestCall. Переиспользуем экран VoIPFragment, устройства, proximity, audio focus и жизненный цикл, а MAX-соединение реализуем отдельным engine. Нужны входящие, исходящие, отмена, busy, пропущенный, reconnect, аудио/видео, камера/микрофон, Bluetooth и групповые вызовы. Вид журнала S44 — только UI-требование.

Фоновая доставка: отдельно исследовать MAX push/device registration и параметры нашего приложения. Firebase-конфигурация чужого клиента не становится нашей после копирования файла. Требуются реальные сценарии background/locked screen/перезапуска; постоянный WebSocket в открытом приложении этого не доказывает.

### 6.6. Возможности, права и локальные настройки

Ввести `MaxCapabilities` и `MaxPermissions` по аккаунту/peer. Представление кнопки определяется подтверждённой поддержкой, а не наличием аналогичной кнопки Telegram. Особое внимание: публикация в канале, удаление у всех, семейная защита, скрытие историй, сроки удаления профиля, каталог рекомендаций, Сферум/Цифровой ID.

Локальные настройки: тема, размер текста, send-on-enter, кэш, autoplay, галерея и сеть для загрузки обновлений. Серверные: профиль, права приватности, сеансы, папки и действия над сообщениями. Смешанные: notifications/mute, быстрые реакции, recent/favorite stickers. Для смешанных явно определить, что синхронизируется с MAX, а что действует на этом устройстве.

Локализация: список выбора строго из восьми вариантов. Все перенесённые меню и новые MAX-only строки имеют переводы и placeholder/plural проверки. Наличие восьми названий языков или перевода только auth-экранов не означает полной локализации Nagram; нужны аудит всех используемых строк и fallback на английский. Telegram remote language requests исключаются.

## 9. Приёмка без фиктивной готовности

- **Визуально:** исходные Telegram-компоненты, baseline одной версии/темы/density; список, профиль, пузырь, папки, popup, settings, stories и call UI проходят overlay-review. MAX-only страницы следуют тем же правилам.
- **Сеть:** вход, открытие чата, send/read, медиа, stories, звонок, startup/resume, deep links и смена языка выполняются при заблокированных Telegram endpoints. Egress проверяется в обычном режиме, включая ошибочные/запасные пути. Допускаются необходимые MAX/media/call/push hosts, установленные по исследованию, а не один захардкоженный домен.
- **Данные:** lossless IDs, account isolation, ordering, edits/deletes, reply target, cursor persistence и согласованность unread после reconnect.
- **Приватность:** переключатели MAX реально изменяют серверное правило; локальный экран не выдаёт успех до подтверждения. Семейная защита и safe mode имеют своё значение, не переименованные Telegram defaults.
- **Языки:** ru/en/es/uz/pt/pt-BR/fr/be, отсутствие лишних языков, все новые строки покрыты, UI выдерживает длинный текст и plural/emoji.
- **Приложение:** actual Nagram APK собран и установлен; live вход и основные функции проверены отдельно от JVM/API shape-тестов. Нет тестовых чатов и демонстрационного OTP в рабочем варианте.

В локальной рабочей ветке уже подготовлены Java MAX transport, начальные операции и слой совместимости Nagram. Пройдены 11 синтетических JVM-тестов протокола/ID, проверка совместимости четырёх файлов адаптера с 99 извлечёнными API-формами закреплённого Nagram и воспроизводимая подготовка исходников с 36 ограждёнными JNI network entry points. Собран и проверен прежний отдельный auth-harness. **Полный Nagram APK и реальный вход в MAX не проверены; 2FA, исходящий auth-звонок/email flow, media/stories/calls ещё не реализованы этим начальным адаптером.** Проверка API-форм не компилирует все UI/контроллеры и не доказывает отсутствие всех Telegram-сетевых путей.

Этот анализ расширяет первоначальный scaffold: перед продолжением реализации нужно считать S03–S05 обязательными входными сценариями и выделить stories/calls/media в самостоятельные задачи. Настоящий MAX-клиент с Telegram UI достигается последовательной заменой подсистем и проверкой серверного результата, а не заменой домена API в одном файле.
